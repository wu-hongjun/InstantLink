    Unused GPU/media boot modules¶

    Goal and boundaries¶

    Remove the remaining legacy VideoCore media initialization failures, preserve the SPI LCD, camera FTP/HIF handling and automatic Printer reconnect, and measure normal boot milestones. No film or Printer image/actuator commands. Three independent agents cover pinned driver/loader sources, implementation and adversarial review. Root performs hardware changes.

    Baseline application source: 966b316; native source b2b6c8c and the reviewed Wi-Fi AP cleanup backport remain unchanged. Pi Zero 2 W Rev 1.0, ST7789 240 × 240, X306 2300 mAh, Debian 13.2, kernel 6.12.47+rpt-rpi-v8, BlueZ 5.82, Python 3.13.5; Printer Link Square INSTAX-52006924. Current boot uses gpu_mem=16, camera/display autodetect disabled, no KMS overlay, auto_initramfs=0. Camera inputs are external uploads, not a CSI sensor.

    Cause and candidate¶

    The pinned VCHIQ driver registers legacy camera/codec/ISP/audio/shared-memory children without firmware service discovery. The 16 MB firmware profile uses cut-down firmware. Udev coldplug therefore attempts unused legacy drivers whose services are unavailable, producing VCHI/shared-memory/MMAL errors. They occur at about 8.4–8.6 seconds in the retained baseline boot. No video or vcsm device survives; no detected vchiq consumer.

    Use a tracked modprobe profile to blacklist alias loading of only bcm2835_v4l2, bcm2835_codec, bcm2835_isp, vc_sm_cma and snd_bcm2835. Ordinary blacklists keep explicit diagnostic loads available. Retain VCHIQ and shared media, DRM, framebuffer, SPI, Bluetooth and Wi-Fi drivers. The ST7789 staging/SPI-ID messages concern essential LCD drivers and remain visible.

    Provisioning installs the owned fragment; boot-diet reports file directives without claiming active enforcement. Reboot is required; rollback restores the previous owned fragment or removes it if initially absent. Do not alter GPU memory, boot overlays, camera/network credentials or service ordering. Reassess alias/dependency/builtin changes when updating kernels.

    Validation design¶

    • Two baseline and two candidate normal reboots with identical application/native source and instrumentation. Kernel-monotonic timestamps exclude power-button and firmware latency.
    • Record first LCD/FTP/core readiness, hotspot and Bluetooth availability separately; systemd total time is not the product-ready metric. Printer-off results do not measure connected readiness.
    • Dry-run effective modprobe alias blacklisting and essential hardware dependencies, with explicit media loads still allowed; verify actual module census and warnings after reboot and rollback.
    • Compare HIF/JPEG preparation output and LCD data; isolated checksum-only FTP fixture cannot print.
    • Final status-only Printer reconnect while locked, same-button unlock/timeout, normal services, source hashes, Wi-Fi backport and full available running/boot log review.

    Measured candidate¶

    Two normal baseline reboots versus two candidate reboots, same application/native source:

    Kernel-monotonic readiness Baseline median (range), s Candidate median (range), s
    LCD UI 13.815 (13.725–13.905) 13.681 (13.543–13.819)
    FTP 13.781 (13.693–13.869) 13.630 (13.530–13.730)
    Hotspot receive ready 20.005 (19.884–20.127) 19.411 (19.088–19.734)

    These small samples overlap for LCD/FTP and do not establish a repeatable boot speedup. Printer was available only in baseline1 (fresh status 20.029 s); other trials had no fresh Printer status, so connected startup times cannot be compared. Software reboots exclude firmware and physical power-on latency.

    Both candidate boots removed all 17 modules in the unused media/audio dependency closure (1,122,304 mapped module bytes in baseline), four VCHI service failures and four NULL video unregister messages. This census is not a measurement of total RAM or battery savings. Essential LCD, Wi-Fi, Bluetooth and USB dependencies remained unchanged. Effective loader dry-runs passed all five leaf names/aliases and ten essential dependency cases; explicit loads by real module name remain available. Independent adversarial source/loader review passed with no outstanding source findings.

    Retained DSC02821.HIF prepared for Mini, Square and Wide before/after: encoded JPEG and decoded RGB hashes, dimensions, selected quality and transport orientation flags were identical. Original identity/content preserved. This CPU fixture used no BLE/image commands or film.

    Installed acceptance¶

    Clean source 79880bd installed after full normal hooks: 2,374 Bridge tests passed with 27 existing platform/Pillow warnings, Ruff and strict mypy (67 modules). Thirteen focused script/profile tests, Bash syntax, formatting, diff and strict MkDocs checks passed.

    Rollback removed only the initially absent owned profile, rebooted, and reproduced all 17 media/audio modules and four VCHI/four NULL unregister messages while preserving LCD/FTP. Reinstall and normal clean-source reboot removed them again; LCD 13.742 s, FTP 13.659 s, hotspot receive readiness 19.920 s. Unchanged native hashes and exact-kernel Wi-Fi backport verified. The module profile is an OS provisioning change, separately installed on this Pi; ordinary source/firmware application updates alone do not activate it on older installations.

    Installed shared GPIO action queue/physical LCD checks passed: same-button triple unlock, nonblank framebuffer equal to the independent render reference, active 1000 MHz, relock 600 MHz and 10-second partial-unlock timeout back to 600 MHz. Physical switch contacts were not actuated. Two isolated 8 MiB FTP receives completed with matching checksums and zero production FTP greeting/NOOP failures. This exercises installed receive code over the same-Pi hotspot address, not an actual camera or wireless airtime. No production upload/print queue used.

    Connected Printer acceptance¶

    An initial 100-second readiness wait expired while the Printer was off; no Disconnect was dispatched. After the user powered on Link Square INSTAX-52006924, installed runtime PID2138 recovered automatically in 6.269 seconds after external BlueZ Device1.Disconnect. Every sample remained locked at 600 MHz, camera-ready and in the same PID. Invalidated timestamps were consistently marked stale; fresh status restored one disconnect watch and zero retired tasks. Radio advertising timing is uncontrolled, so this is reliability validation, not a speedup claim. Film remained zero; no image/print/actuator commands.

    Connected same-button triple unlock/exact nonblank pixels/1000 MHz, relock/600 MHz, 10-second partial-unlock abandonment, status pause/resume and fresh single-watch rearm all passed.

    Available installed-boot logs initially contained 203 Bridge/manager records and one manager.bind_pending: USB listener was already serving, hotspot listener succeeded one second later. Kernel had 376 records and ten expected regulator/read-only switch/backport taint/LCD staging/SPI-ID notices; no VCHI/media NULL unregister or Wi-Fi vendor-IE errors. Complete raw logs remain private. Offline Pi wall clock can reset on reboot; all boot comparisons use kernel monotonic time, independent of that clock. No film was used.

    Connected FTP continuity repeated: both isolated 8 MiB receives/checksums passed, zero production FTP failures; all 17 monitored samples retained connected/fresh Printer, locked 600 MHz and camera readiness. An early normal-health assertion ran 47 seconds after service start and expected idle too soon; active 1000 MHz was correct. Final capture waits for the actual idle policy transition rather than treating that fixture timing as an application bug.

    Final normal service and log review¶

    Restored normal Bridge PID2626 / manager637, both active with zero automatic restarts, connected Printer, powersave600 MHz/GPIO24 low, FTP220/200, GPIOv2 and no input/network fallback, throttle0x0. Source/native hashes and clean manifest match.

    Full final installed-boot logs include five Bluetooth warning records after the observed-to-normal service restart: two missing-write-characteristic connection setup failures plus existing auto-rebond. Normal runtime recovered automatically after 66.480 seconds from its boot-start marker, with fresh film0/battery50% status and connected final health. This remains a connection-setup follow-up (GATT service/cache readiness); the media profile changes no Bluetooth source/dependencies. Do not describe these logs as fault-free or conflate this restoration timing with the successful6.269s external-disconnect test. The expected manager listener wait remained the other flagged service record. No VCHI/media unregister or vendor-IE errors returned.

    Owned observer/drop-in/socket and 19 test/helper files removed; only the production root0644 media fragment remains, matching reviewed SHA. User photos and Wi-Fi backport rollback provenance untouched. Clean source deployed with normal services; no firmware publication.
