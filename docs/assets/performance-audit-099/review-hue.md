# Independent adversarial review: Bridge hue optimization 07

Reviewed the final production diff against `f5ed2c8` on 2026-10-15: grouped hue-sector selection, in-place quantization, and the RGB-only 512×256 tile wrapper in `bridge/src/instantlink_bridge/imaging/postprocess.py`. Also inspected the frozen oracle, edge/combined-profile tests, lazy import coverage, benchmark helper and its raw allocation/RSS definitions. This reviewer did not implement the hue change.

**No actionable regression found.**

- **Reference independence:** Independently parsed the baseline `_apply_hue` from `git show f5ed2c8:...` and the test's `_reference_hue`. Their complete function ASTs match after changing only the function name. The oracle retains the original five-level selection and allocating quantization expressions.
- **Exact arithmetic:** All RGB inputs are finite uint8 values converted through the unchanged float32 HSV calculations. Sector index modulo six remains in 0–5. Grouped R/G/B selection matches all six original sector values, including the paired equal choices. The private float32 `out` array is distinct from input and HSV arrays; clipping, multiplication by 255 and addition of 0.5 preserve the original sequence and dtype before uint8 conversion. No reduction, interpolation or neighborhood operation makes results depend on tile shape.
- **Bounds and complete coverage:** Nested ranges start at zero and advance by strictly positive tile dimensions; `min` clips only the right/bottom edge. Each source pixel is cropped and pasted exactly once at the same coordinate. A 513×257 or odd larger image therefore includes narrow/short trailing tiles without gaps, overlap or resampling. Bounding both dimensions also handles single-row panoramas and single-column portraits without a full-width floating-point intermediate.
- **Ownership and special inputs:** Crops create separate image data and NumPy float arrays are private. The output is a new RGB canvas; source pixels are never assigned. Small RGB images avoid the wrapper allocation. Zero-axis images and non-RGB modes go directly through the prior array boundary, avoiding crop-induced behavior changes. Non-RGB layouts with previously unwritten channels are outside the documented RGB contract; the review does not claim deterministic equivalence for those undefined bytes.
- **Metadata and pipeline:** The original `Image.fromarray` output discarded input metadata. The tiled `Image.new` result does so too; `paste` does not import tile metadata. The new tests compare decoded JPEG/PNG/BMP/TIFF outputs and empty metadata. NumPy remains imported inside the helper; module import adds only constants/functions. Adjustment order, geometry, downstream overlays and JPEG settings are untouched. Existing tests compare combined-profile pixels and encoded JPEG bytes against the oracle.
- **Memory claims:** At most one 512×256 float computation is active per loop iteration; temporary tile results are pasted and released rather than accumulated. Source and output Pillow images remain full-sized, so total operation memory is not constant. The benchmark's `tracemalloc` samples exclude input fixtures and native Pillow allocations; its separate fresh-child high-water RSS includes imports, source data and native memory. The recorded approximately 762.8→10.8 MiB tracked allocation result supports bounded intermediates, while neither metric establishes Raspberry Pi peak memory or battery savings. Fresh-child RSS is a process high-water measurement, not an isolated allocation delta or whole-pipeline bound.
